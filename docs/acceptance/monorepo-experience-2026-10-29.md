### 解锁后的再次尝试

用户再次确认解锁后，桌面工具成功列出了原生应用。连接本地验收包分别在 30 秒、60 秒等待后超时；随后连接列表中已运行的 Finder 也超时。期间只读进程检查未发现验收包进程。这说明当时原生操作链路无法使用，不能归因为已证实的 Diffkin 启动缺陷。后续授权后控制恢复，原生功能验收结果见下一节。

## 功能与输入矩阵

- 1200×800 阅读聚焦代码区维持至少 900×560；760×540 深色无页面横向溢出。检查了最终浅色和深色截图。截图保存在本地 `artifacts/monorepo-experience-final/`。
- 420 / 2000 个变化可直接搜索末页路径；虚拟列表仅挂载可见附近行；历史、下个未审查与目录切换可用。
- 关系选择和结构分析完成不重建全文编辑器；搜索恢复、滚动恢复、移动连线、格式折叠反例通过。
- 刷新成功保留原文件路径并重置快照历史；失败或取消保留旧视图；旧分析或预览不能覆盖新选择。
- 冻结文本可先读，最终分析完成前不能标记已审查；缓存按 32 MiB 计费预算及 64 条上限淘汰。计费为序列化大小的两倍估算，不等同于进程 RSS 上限。
- 四种比较模式均支持字面文件/目录范围。相似前缀不会混入，`*` 不作为通配符；无效相对路径被拒绝。范围参与快照身份，范围外内容及跨边界改名语义有明确提示。
- 真实 2001 变化提交全量返回预算错误，传入单文件范围后成功；10,001 个范围外文件的集成用例验证全量失败、范围恢复与冻结语义。
- 大文本以独立双侧分段原文呈现，每段约 32K UTF-16 字符且不拆代理对。两侧段号不构成差异对应，截断原文始终提示不能核对全文。
- VS Code 固定提交的 25 个变化、React Native 固定提交的 2 个变化均由最终 CLI 再次捕获；快照身份与基线一致，浏览器联测完成逐文件审查。见 [最终捕获](results/monorepo-final-captures.json)。这两个公开输入变化较少，不能代表 2000 文件结构分析吞吐量。

## 性能测量与仍有的限制

[30 次 worker 测量](results/monorepo-worker-timings.json)使用 release 构建和固定 VS Code TS 文件。原文读取 p95 约 0.0007 ms、结构分析约 0.794 ms、缓存命中克隆约 0.0072 ms。这仅是原生内存读取/分析路径，**不含 IPC、首次可见布局和 WebView**；不据此宣称 300 ms / 1 s / 100 ms 的端到端门槛已经达标。它也不是受控机器上的基线/候选交替比较。

全量快照仍限制 2000 个变化路径、64 MiB 内容预算和 20 秒捕获时间；每侧大文件冻结预览仍受既有 2 MiB 上限约束。P5 通过缩小范围与分段显示恢复可用性，本轮没有磁盘冻结存储，也没有宣称支持任意 10k 变化的完整捕获。范围筛选不跳过内容复核，不在稍后点击时读取活动工作区冒充旧快照。

原生核心功能流程已完成；仍需补充原生最小窗口、系统缩放矩阵。性能准入还需按 [质量计划](../quality.md)进行至少 30 次真实 IPC 到可见结果测量、全进程内存与取消释放测量；在完成前维持“核心功能通过、性能准入待验证”的状态。
