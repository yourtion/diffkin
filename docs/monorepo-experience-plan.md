# 大型 monorepo 审查体验改进计划

日期：2026-10-29。评估基线：`a80937f`，0.3.0-alpha.2。状态：**P1 布局基础已落地；P2–P5 待实施，原生验收待完成**。

本轮以整体布局与视觉设计为第一优先级，再改善文件定位、连续审查和响应速度。建议保留现有 React、CodeMirror、Tauri 与 Rust 内核，先围绕“找到改动 → 阅读代码 → 查看依据 → 标记并继续”重组界面。当前大仓库能力主要覆盖“大量跟踪文件、少量变化”，不能据此承诺巨型变更集的完整体验。

## 实施进度

2026-10-29：P1 布局基础已接入实际 React 界面，默认阅读聚焦。比较设置、文件导航和详情按需展开；宽屏导航支持拖拽与键盘调宽，窄屏导航/详情使用浮层；文件名优先显示，完整路径保留在可访问名称与提示中。深色代码高亮采用语义色，代码字号调整为 13 px。

1200×800 浏览器窗口、无告警时，代码区实测从 696×416 增加至 1200×568。760×540 深色布局无页面横向溢出。59 项浏览器检查通过，包含真实内核、持久工作区/验证输出和两个公开仓库；前端检查与构建通过。原生 WebView、系统缩放与用户实际审查体验仍待验收。

P1 当前保留分页，已明确提示“仅筛选已加载文件”；完整搜索在 P2 实施。P2–P5 的导航、编辑器生命周期、刷新连续性、分阶段响应与容量扩展尚未实现，不能把新的视觉布局当作这些问题已解决。

## 公开仓库测量

使用 [VS Code](https://github.com/microsoft/vscode) 与 [React Native](https://github.com/react/react-native) 的两提交浅克隆，不安装依赖、不执行项目脚本。两个仓库的 index 哈希前后相同，工作区保持 Git clean。

| 仓库                    | 跟踪文件 | 固定提交变更数 | 提交捕获 p50 / p95 | 工作区捕获 p50 / p95 |
| ----------------------- | -------: | -------------: | -----------------: | -------------------: |
| VS Code `b6bfa95e`      |   21,145 |             25 |  92.84 / 112.07 ms | 3669.90 / 3713.88 ms |
| React Native `25b05acd` |    8,264 |              2 |   89.46 / 89.58 ms |   823.79 / 829.12 ms |

计时为 release 构建、每模式连续 30 次、文件系统暖缓存，仅含 Rust 捕获。VS Code 工作区包含上述 29 个原始换行差异，React Native 为零变化；这不是相同负载的仓库间性能排名。VS Code 工作区最大样本为 6484.15 ms。开发机早期样本与浏览器评估活动有重叠，因此这些数据用于确定调查方向，不作为发布达标证据。

真实提交的 27 个文件均通过浏览器逐文件打开、标记审查和计数联测。两个样本覆盖前端工具与跨平台客户端，但不代表 10 万至 50 万文件的巨型仓库；下一阶段必须补合成规模场景。

结论是：提交捕获在这些样本上不是首要阻碍，工作区捕获值得独立分析；布局和导航已有可复现问题，适合先落地。

## 布局与视觉方向

推荐默认采用“目录导航”，提供“阅读聚焦”作为同一审查工作台的视图模式。两种模式共享文件选择、筛选、审查进度和内容，不做两套独立产品流程。会话中的交互草案用于讨论空间与操作组织，代码和审查状态为示例，不代表实现完成。

### 目录导航

- 顶部压缩成应用栏与比较上下文栏：仓库名称、比较模式、来源与目标、刷新、任务状态。路径输入、未跟踪文件选项和完整核验放入“比较设置”，当前生效范围仍有简短摘要。
- 左侧默认约 260 px，支持拖拽、折叠、目录树和平铺切换。文件名为主，父目录为辅；压缩单子目录，保留完整路径的复制与可访问名称。
- 中央文件头只保留路径面包屑、文件名、变化统计与“标记已审查”。文件模式在确有变化时突出，完整对象身份放入详情。
- 工具栏集中双栏/统一、变化导航、搜索和视图选项，低频选项进入菜单。已证明格式折叠仍有可见计数和恢复入口。
- “变更关系”和“依据/元数据”合并到可切换详情面板，默认收起；宽屏可固定在右侧。打开、关闭或结构分析完成时不突然改变代码滚动锚点。
- 警告按范围放置：影响正确性、截断或捕获失败的状态必须常驻可见；一般读取语义合并成短摘要与详情入口，不连续堆叠大段说明。

### 阅读聚焦

文件导航收起，使用快速打开、前后历史和下个未审查文件继续审查；详情按需打开。窄窗口优先使用该布局或统一 diff，保留用户手动选择。首次进入显示切换入口，不静默永久覆盖用户偏好。

### 视觉规范

- 延续 Diffkin 的绿色识别色，但主体使用中性表面，绿色用于主要动作和选中状态；增删、冲突、回退有独立语义，配合文字或图标区分。
- 正文字号以 13–14 px、辅助信息至少 11–12 px、代码默认 13 px 为候选；代码字号可调。停止用缩小字号解决窄窗口拥挤。
- 建立统一的颜色、间距、字号、行高、边框、焦点与禁用态 tokens，同时覆盖浅色和深色。
- 文件行候选为 28–32 px，控件和标题层级统一；选中、键盘焦点、已审查分别表达，不把所有状态涂成绿色。
- 明确定义初次打开、捕获中、空变化、筛选无结果、取消、失败、部分预览、文本回退和已审查状态。取消作为任务状态显示，不用通用错误横条承载。
- 1200×800、1440×900、最小 760×540、系统缩放与深色均单独验收；原生窗口尺寸与浏览器 viewport 分开记录。

## 交互改进

1. **全量范围搜索与目录定位。** 查询针对当前快照的完整变化清单，返回匹配总数与分页；渲染使用虚拟列表/扁平目录树。快速打开支持文件名与路径。搜索无结果必须区分“完整查询无匹配”和“清单尚未完成”。
2. **按范围组织。** 第一版只做目录/路径范围和变化类型筛选；后续可静态读取 package/workspace 描述生成模块标签，无法识别时回退目录。不要把目录自动等同于构建依赖图。
3. **连续审查。** 标记并跳转下个未审查、浏览历史、当前文件与滚动位置恢复、选中项自动滚入视口。快捷键在输入框与编辑器中的作用域明确。
4. **刷新保持上下文。** 旧快照继续可读，后台创建新快照；成功后按稳定路径/内容定位，失败或取消保留旧视图。新旧快照清楚区分；旧审查结论不得仅凭路径自动继承。
5. **渐进显示。** 捕获和分析显示阶段、已处理数量及取消状态。没有可靠总量时不显示虚构百分比。文本先可读，结构结果随后增强；“已审查”仍绑定明确的内容和分析版本。
6. **降噪可解释。** 生成文件、锁文件、大文件、换行转换差异可分组或筛选，始终显示数量及当前范围。仅按路径猜测的类别不能产生安全折叠证明。

## 性能改造与正确性约束

| 优先级 | 改造                                                                                | 必须验证的边界                                                         |
| ------ | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 首批   | 详情切换通过 EditorState transaction / decoration 更新，减少无必要的 MergeView 重建 | 搜索、选区、折叠、移动连线、CRLF 坐标映射仍正确                        |
| 首批   | 完整清单查询与可见行渲染解耦，使用可索引的数据与稳定选择                            | 2000 项查询完整；虚拟化后键盘焦点和可访问性不退化                      |
| 后续   | 文本与结构分阶段响应，当前文件优先，必要时预取相邻文件                              | generation 隔离、取消资源释放、未完成分析状态、审查依据不混用          |
| 后续   | 按字节预算的 LRU；键包含双侧内容、规则/schema、相关选项                             | 不以缓存条数推测内存；同路径新内容不能复用旧结果；低频回退也受预算控制 |
| 后续   | 捕获阶段计时，区分 index/stat、attributes、Git 对象、原文冻结与复核                 | 先测量各阶段；不得通过关闭复核或忽略原始字节换取速度                   |
| 扩容   | 元数据目录与内容存储解耦，支持受限范围捕获和磁盘冻结内容                            | 比较范围进入身份；排除范围可见；巨型输入不能静默裁掉后标“完成”         |

提交模式可以固定对象 ID 后按需读取不可变 blob。工作区模式不能在用户稍后点击文件时读取活动文件并冒充先前快照：必须先完成受控冻结，或把新读取明确作为新捕获。提前展示的路径清单应标为“发现中/未冻结”，不能提前成为审查证据。

大型变更集的扩容先提供路径范围选择与明确的预算恢复入口，再评估磁盘内容存储；不直接放大 2000 路径和 64 MiB 阈值。SQLite、全仓符号索引、全新编辑器和大规模前端状态库不是本轮前置条件。

Module 划分按生命周期进行：`ReviewSession` 隐藏快照、任务、选择与失效处理；`ChangeNavigator` 隐藏查询、目录展开、分页与虚拟渲染；`DiffDocument` 隐藏编辑器、坐标映射和视图状态；Rust `SnapshotCatalog` 隐藏完整清单查询与内容定位。各自提供小 Interface，避免只把 App.tsx 搬成多个透传文件。

## 验收矩阵

- 固定公开输入：上述 VS Code 与 React Native 的精确 base/head；后续加入有大量测试 fixture 的前端 monorepo。避免直接用持续变化的 HEAD 做回归基准。
- 仓库体量：10k、100k、500k tracked；变更体量独立取 20、200、2000、2001、10k。超过当前支持范围的场景先验证诚实失败与恢复入口，不先承诺性能目标。
- 内容形态：长路径与同名文件、TS/Vue、Java/Kotlin、Swift/ObjC/C++ 文本回退、锁文件、生成文件、二进制、大文件、超长行、CRLF、非法语法、纯元数据变化。
- 操作链：打开 → 搜索末页文件 → 切换十个文件 → 返回首个 → 选中关系 → 搜索/折叠 → 标记并继续 → 刷新 → 取消。
- 性能拆项：清单就绪、首个文本、结构增强、缓存切换、滚动长任务、取消与资源释放、全进程内存。缓存未命中与系统冷缓存分别记录。
- 测量方式沿用[质量计划](quality.md)：普通场景至少 30 次，基线/候选交替、固定构建/输入/环境；受控机器达标后再形成产品承诺。当前浏览器联测不能替代原生 WebView 验收。

第一步建议落地 P1：用户可以直接看到和使用新的审查工作台；用真实样本确认布局后，再推进全量导航和性能改造。
